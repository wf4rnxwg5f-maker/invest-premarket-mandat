## Задача 2. Опишите идею и область её применения (лимит 900)

«Мандат» — проверяемые полномочия ИИ-агента на брокерском счёте.
Область: предторговый контроль поручений, которые внешний ИИ-агент клиента подаёт через T-Invest MCP.
Для кого: клиент, который подключил агента, но боится дать ему торговые права; для Т-Инвестиций — новый уровень прав «торговля в пределах мандата».
Задача: клиент своими словами задаёт рамки («не больше 10% в одну компанию, третий эшелон не бери»), а каждую заявку агента до брокера проверяет по ним код.
Как сейчас: токен даёт «чтение» или «полный доступ» без лимитов по бумагам и долям; рамки живут в промпте (модель может нарушить, инъекция из новости — отменить) или в подтверждении каждой сделки (его одобряют не глядя).
Формат: MCP-шлюз, мастер мандата и журнал решений.
Что изменится: клиент даёт агенту торговлю в понятных границах; брокер растит долю торгующих через агентов (сейчас около 5%) без потери контроля.

## Задача 3. Почему команда выбрала эту идею? (лимит 600)

Знаем из своих замеров на данных Мосбиржи: «ВДО» в двух разумных прочтениях даёт разные решения по 30% облигаций, а Магнит формально попадает в «третий эшелон» — смысл слов клиента надо уточнять. На 51 наборе реальных правил инвесторов форма из 15 полей выразила лишь 23% ограничений. Из блога Т-Инвестиций: MCP сам не запрашивает согласия на каждую сделку; сделки через агентов совершают около 5% пользователей.
Предполагаем: торговые права не дают в том числе из-за отсутствия рамок; клиент сумеет написать мандат и проверить его пересказ.

## Задача 4. Как будет работать решение? (лимит 1000)

Вход: текст клиента («Покупай акции на свободные деньги, не больше 10% в одну компанию, заявка до 30 тыс. ₽, ОФЗ не продавай, третий эшелон не бери»), портфель, справочники T-Invest и MOEX ISS; затем — заявки агента.
Действия: 1) LLM переводит текст в 8 правил; что не разрешено явно — «спросить владельца». 2) Для «третьего эшелона» LLM даёт прочтения, код находит бумаги, где они расходятся: «Магнит — третий уровень листинга, но в двадцатке по обороту. Пускать?» Ответ → правило «оборот ≥ 10 млн ₽ в день». 3) Клиент подписывает пересказ правил с примерами. 4) Агент шлёт 4 заявки; шлюз считает портфель после каждой с учётом активных заявок: три проходят, четвёртая (оборот 5,7 млн ₽) отклонена.
Результат: агенту — отказ с номером правила, владельцу — уведомление с кнопкой «разрешить один раз», запись в журнал.
Кто использует: агент, клиент, поддержка брокера.
Дальше: агент перепланирует; клиент получает сводку; расширить мандат можно только с подтверждением.

## Задача 5. Что именно будет делать AI? (лимит 700)

AI: 1) разбирает слова клиента в закрытый язык правил (~20 типов проверок) или помечает «уточнить», «не могу выразить», «принцип»; 2) предлагает прочтения расплывчатых понятий, а код находит бумаги, где они расходятся, и задаёт клиенту 1–3 вопроса. Решение по заявке — только код. В пилоте две LLM на 16 мандатах не пропустили ни одного пункта.
Почему не форма и правила: в пилоте форма выразила 23% реальных ограничений, хвост длинный и разнообразный. Не словарь: расплывчатые формулировки почти не повторяются. Не поиск: ответ — намерение клиента. Не расчёт: он покажет расхождение, но не выберет смысл. Не LLM на каждую заявку: в пилоте её вердикт по спорным бумагам менялся в 31% повторов.

## Задача 6. Какие AI-подходы предполагается использовать? (лимит 450)

Подходы: LLM; другое — семантический разбор в закрытый язык правил и детерминированный движок политик.
Почему: LLM нужна только на входе — перевести свободный текст мандата в правила и предложить прочтения расплывчатых понятий; код находит бумаги, где прочтения расходятся, и человек отвечает только там. Решение по заявке принимает движок без LLM — оно воспроизводимо и не зависит от инъекций.

## Задача 7. Технический контур MVP (лимит 1200)

Компоненты: 1) MCP-прокси (Python, MCP SDK): чтение пробрасывает, заявки и стоп-заявки перехватывает, неизвестные инструменты запрещает; 2) движок политик — чистая функция «политика × состояние × заявка → пропустить / спросить / отклонить» (прототип уже есть: 15 тестов, 3 000 случайных последовательностей заявок не нарушают лимиты); 3) компилятор и модуль уточнения (LLM + код); 4) пересказ правил шаблонами, без LLM; 5) веб-интерфейс владельца: мандат, уведомления, журнал, «стоп агенту».
Модели: облачная LLM и T-pro-it-2.1 — две независимые компиляции, расхождение = вопрос клиенту; вывод по JSON-схеме; портфель в модель не уходит.
Хранилища: SQLite — версии мандата, журнал только на дозапись с цепочкой хэшей, кэш справочников.
API: T-Invest MCP/API (песочница, портфель, справочник, стримы заявок), MOEX ISS (уровень листинга, индексы, обороты).
Взаимодействие: агент → прокси → движок → брокер, либо отказ и уведомление владельцу → журнал.
Результат: подписанный мандат; решение по каждой заявке за миллисекунды с номером правила. В продукте проверка живёт в API-шлюзе брокера.

## Задача 8. Какие данные потребуются? (лимит 700)

1) Мандаты: анкета 45+ инвесторов вне команды (текст + ответы на пробные заявки), разово; выборка удобная, с перекосом в опытных. 2) Справочник: T-Invest API (тип, сектор, флаги облигаций, ликвидность), раз в день; уровня листинга и эмитента нет → MOEX ISS (по договору) или данные брокера; группы компаний — свой справочник. 3) Состояние счёта: портфель, позиции, активные и стоп-заявки — стримы T-Invest API, в реальном времени, лимит 50–600 запросов в минуту. 4) Стакан и цены — при каждой рыночной заявке; нет данных → «спросить». 5) Песочница: исполняет по последним сделкам, маржу не считает. Формат — JSON. В облачную LLM уходит только текст мандата.

## Задача 9. Как вы проверите, что решение работает? (лимит 700)

Гипотеза: компилятор с уточнением решает пробные заявки так, как решил бы сам автор мандата, без тихих разрешающих ошибок, и задаёт меньше вопросов, чем форма.
Данные: 45 мандатов инвесторов вне команды, 30 запечатаны до заморозки системы; автор отвечает на 12 пробных заявок «разрешил / запретил / спросите меня» — это истина.
Baseline: форма лимитов (заполняет автор); LLM-судья по каждой заявке; компилятор без уточнения.
Метрика: доля мандатов с тихой разрешающей ошибкой.
Достаточно: 0 из 30 (это «≤9,5%» с 95% уверенностью) и на 20+ п.п. больше верных решений без вопроса, чем у формы. Если форма выражает ≥85% мандатов — делаем форму.

## Задача 10. Какие риски и стоп-факторы могут сделать идею нежизнеспособной? (лимит 800)

1) Спрос: права не дают из недоверия к ИИ, а не из-за рамок → мандат не нужен. Проверка: страница беты в сообществах пользователей T-Invest API; стоп, если записывается меньше 5%.
2) Поток вопросов: если шлюз спрашивает чаще раза в день, вопросы одобряют не глядя → защита формальна. Проверка: прогон 10 мандатов по двухнедельной истории сделок.
3) Ложная гарантия: правило скомпилировано мягче или обходится (дробление, отложенные заявки) → хуже, чем без шлюза. Проверка: мутационные тесты и тест подсаженной ошибки в пересказе (замечают ≥80%).
4) Интеграция: прокси с чужими токенами нарушает правила API → без брокера только прототип. Проверка: local-first MVP в песочнице, вопрос команде MCP на очном этапе.
